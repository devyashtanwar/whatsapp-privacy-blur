# Hover recovery and Gaussian-style execution

Plan: docs/research/2026-11-04-hover-recovery-and-blur-style-plan.md.
Base: PR #5 head eb6318f272e914fc3e568554283fd2fee80cd963. User approved implementation for testing. Existing agent-owned branch/checkout reused. Browser/desktop operation, visible GUI launch, installation, additional permissions and production integration remain excluded.

Regression evidence: the existing integrated controller failed two new hidden-view tests: an unfinished scroll marker required window switching, and direct post-scroll message entry required a blank-space sample. No claim is made that the exact user's trackpad event stream was captured.

Functional implementation: HoverRecovery replaces independent permanent locks and the blanket exit latch. Each pane has a bounded last-motion timestamp. Real movement revokes reveal; preparation is not a persistent lock, stationary callbacks are ignored, and duplicate/late end observations cannot revoke a new hover. A 150 ms quiet interval restores eligibility, never a reveal. Only newer local pointer movement with changed coordinates can acquire a bounded item lease. Same coordinates, a timer or content moving under the cursor cannot acquire one. Focus/disabled/unsupported states keep reveal revoked. Expiry still requires leaving the expired item or entering another one.

The real event adapter now scopes raw gesture/momentum signals to the same pane used by clip/live-scroll notifications. Physical clip movement, including legacy/programmatic input, keeps the content-attached masks and revokes reveal before movement. The 50 ms timer only expires reveal/prunes stale motion; it does not position masks or acquire hover.

Ruling: Use bounded actual-motion observations rather than perfectly paired gesture counters. Missing/cancelled/duplicate platform signals must not create an indefinite lock. Cost: the proposed 150 ms settling interval needs hardware acceptance; genuine motion always reblurs through existing hooks and user intent is required after recovery.

Visual implementation: added GaussianMessageView and Core Image CIGaussianBlur, using text/font/bubble colors generated from the lab's own invented data. No view/window/screen capture or external pixels. Default is Gaussian with 65% tint; a 60–70% slider and existing material comparison options remain. The image is flattened opaque before filtering; tint is composited over the blurred base, never sharp text. Clamped edges and cropped output avoid filter-edge transparency. Rounded localized surfaces and a subtle border preserve message structure. Failure falls back to an opaque local placeholder and explicit lab status, never clear text.

Three synthetic pixel regressions failed against an identity/pass-through scaffold before the filter: unsmoothed edges, transparent output and invalid parameters. One initial assertion expected a nearly flat whole stripe row; actual clamped-edge filtering produces a smooth boundary gradient. Replaced that mistaken flatness criterion with adjacent-edge contrast and non-extreme pixel checks; an identity filter still fails. This is a correction to test semantics, not a weaker privacy claim. Pixel tests do not prove human unreadability for every font/content.

Ruling: Gaussian styling is enabled only for invented lab content. It does not supply WhatsApp pixels or resolve cross-process message geometry; no new capture/Accessibility access is authorized. Cost: visual acceptance and external integration remain separate gates, and the Gaussian appearance is not production certified.

Final verification: 35 policy assertions and 131 hidden AppKit/view/event/pixel assertions passed. The repository suite passed all 57 Python tests with 3 explicit fixture/live-process skips; the core Swift suite also passed. Both the lab and unchanged production app built successfully and passed signed-bundle/capability verification. No GUI window was created or app installed/launched.

Independent source review found no critical or important defect. One nonblocking precision limitation remains: the pointer adapter uses processing uptime rather than NSEvent.timestamp, so fresh motion means changed coordinates when handled, not independently verified event-origin time. Hardware acceptance must cover delayed event delivery along with click, momentum and direct post-scroll hover recovery. Do not claim zero-frame disclosure or universal unreadability from these tests. No GUI window was created by the tests; the complete text renderer is exercised in a generated in-memory drawing context.
